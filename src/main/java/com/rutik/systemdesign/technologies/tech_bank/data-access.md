### aiomysql
**Short:** Asyncio MySQL/MariaDB driver for async SQLAlchemy stacks; asyncmy is the more actively maintained alternative.
**Kind:** tech
**Lang:** python
**Roles:** data-access/drivers-and-connection-pooling @1, runtime-systems/concurrency-and-async @3

Under the hood it is PyMySQL's pure-Python protocol implementation driven by coroutines, so packet framing and result parsing happen on the event loop instead of in a worker thread. It exposes both a low-level `aiomysql.create_pool` and the SQLAlchemy dialect behind `mysql+aiomysql://` URLs, which is how an async FastAPI or Starlette service reaches MySQL through the ORM.

Reach for it mainly where it is already in the stack. Because the codec is pure Python, decoding a large result set burns CPU on the loop itself and stalls every other task; asyncmy reimplements the same protocol in Cython and is the more actively maintained choice, so new services should start there and keep aiomysql for compatibility.

### aiosqlite
**Short:** Async SQLite driver for asyncio; zero-config in-memory database for fast tests.
**Kind:** tech
**Lang:** python
**Roles:** data-access/drivers-and-connection-pooling @1, data-stores/key-value-and-embedded @3

It is a thin adapter, not a new engine: each connection runs the standard library's `sqlite3` driver on its own worker thread and exposes it as `async with aiosqlite.connect(...)`, so an asyncio application can await queries without blocking the event loop on file I/O. It is also the driver behind SQLAlchemy's `sqlite+aiosqlite:///` URLs, which is how an async FastAPI test suite runs against an in-memory database with no PostgreSQL container to start.

Understand that it buys concurrency of the event loop, not of the database. SQLite still serializes writers and the work still happens on a thread, so reaching for it to make a write-heavy service faster is a misread; use it for tests, local tools and low-write embedded workloads.

### Akka Distributed Data
**Short:** Akka module replicating CRDT key-value state across cluster nodes so concurrent writes converge without coordination.
**Kind:** tech
**Lang:** java
**Roles:** data-access/transactions-and-consistency @1, caching/distributed-cache @2, data-stores/key-value-and-embedded @3

Each node keeps a local replica of a set of keys and gossips deltas to the others. Because every value is a CRDT — a counter, set, map, register or flag with a commutative, idempotent merge — two nodes that took conflicting writes converge on the same state with no leader, no lock and no consensus round. Reads and writes take a consistency level, from purely local up to a quorum or all replicas.

Reach for it for small, high-churn cluster state that must survive a partition: presence, cart contents, feature flags, per-node counters. The cost is that every node holds everything in heap, so it does not scale with data volume, and merge semantics constrain what you can model. Note also that Akka is BSL-licensed now; Apache Pekko is the open fork.

### Alembic
**Short:** SQLAlchemy's migration tool: autogenerated, version-controlled, reversible schema revisions.
**Kind:** tech
**Lang:** python
**Roles:** data-access/schema-and-migration @1

A migration is a Python module with `upgrade()` and `downgrade()` functions and a `revision`/`down_revision` pair, so the history is a directed graph rather than a flat sequence — which is what lets two feature branches each add a revision and be merged later. The applied head is recorded in an `alembic_version` table in the target database, and `alembic revision --autogenerate` produces a first draft by diffing your SQLAlchemy metadata against the live schema.

Treat autogenerate as a draft, never as output. It reliably sees tables, columns and indexes but misses or mangles server defaults, enum changes, and anything needing a data backfill. Review and edit every generated script, and write the data migration by hand alongside the DDL.

### Apache Kafka KRaft
**Short:** Kafka's built-in Raft metadata quorum, replacing ZooKeeper for controller election and cluster metadata.
**Kind:** tech
**Lang:** *
**Roles:** data-access/transactions-and-consistency @1, data-movement/event-streaming-and-processing @2

A small set of brokers is designated as controllers and runs Raft among themselves over an internal metadata topic, so cluster metadata — topics, partitions, ISR membership, configs — becomes an ordered log that every broker replays and caches locally, instead of a tree of znodes each broker watches. Controller failover is a Raft election, and a restarting broker replays from a snapshot rather than re-reading state from an external service.

The practical wins are one system to operate instead of two, much faster controller failover, and metadata that scales to millions of partitions. Migration off a ZooKeeper cluster is a staged dual-write process rather than a flag flip, so plan it as a project; new clusters simply start in KRaft mode.

### asyncmy
**Short:** Actively maintained async MySQL/MariaDB driver for asyncio and SQLAlchemy's async engine.
**Kind:** tech
**Lang:** python
**Roles:** data-access/drivers-and-connection-pooling @1

It reimplements the MySQL client protocol in Cython, compiling the packet framing and row decoding that aiomysql leaves in pure Python, which is where its throughput advantage on large result sets comes from. The API deliberately mirrors aiomysql and PyMySQL — `connect`, `create_pool`, the cursor classes — so switching is usually an import and a URL, and SQLAlchemy's async engine reaches it through the `mysql+asyncmy://` dialect.

Reach for it as the default async MySQL driver in an ASGI service, creating the pool once in the lifespan hook rather than per request. The tradeoff is that a compiled extension needs a wheel or a build toolchain in your image, and nothing in the MySQL ecosystem has asyncpg's polish, so measure before assuming the driver is your bottleneck.

### asyncpg
**Short:** Async PostgreSQL driver speaking the binary protocol; the fastest Python Postgres client, with its own pool.
**Kind:** tech
**Lang:** python
**Roles:** data-access/drivers-and-connection-pooling @1

asyncpg speaks the PostgreSQL binary wire protocol directly rather than going through libpq, decoding results into Python objects without a text round-trip, and it prepares statements automatically, which is where most of its speed advantage comes from. It is built on asyncio, so a query yields to the event loop instead of occupying a thread-pool worker the way a synchronous driver does.

Use it under SQLAlchemy's async engine, or directly through its own `create_pool` in an ASGI service, creating the pool once in the lifespan rather than per request. Two consequences of the binary protocol are worth knowing: parameters are numbered `$1`, `$2` rather than `%s`, and the automatic statement cache breaks against a transaction-pooling PgBouncer unless you disable it.

### Atlas
**Short:** Ariga's schema-as-code tool: declare the desired database schema, and it diffs, plans and applies the migration.
**Kind:** tech
**Lang:** *
**Roles:** data-access/schema-and-migration @1

Atlas treats the schema as a declared desired state in HCL or plain SQL: it inspects the live database, diffs it against the declaration, and generates or plans the migration, which also gives it drift detection and a lint step you can run in CI before anything touches production. That is the same model Terraform uses for infrastructure, applied to tables and indexes.

Reach for it when you want the schema reviewed as a single declarative file rather than as an append-only stack of numbered scripts, and when drift between environments is a recurring problem. Versioned-migration tools such as Flyway and Liquibase remain the safer fit where every step must be hand-written and auditable. Unrelated to MongoDB Atlas and to Netflix Atlas, both of which have their own entries and share only the word.

### Atomikos
**Short:** Java JTA/XA transaction manager coordinating two-phase commit across multiple resources.
**Kind:** tech
**Lang:** java
**Roles:** data-access/transactions-and-consistency @1

It plays coordinator in two-phase commit: your code opens one JTA transaction, enlists XA-capable resources such as a database and a message broker, and Atomikos runs the prepare and commit rounds while writing a transaction log so an in-doubt branch can be recovered after a crash. That is what buys atomicity across two resources a single `Connection.commit()` cannot span. Reach for it only when you genuinely need XA inside one JVM, and note that in Spring the integration now comes from the vendor's own starter rather than Spring Boot auto-configuration. It is blocking by design, since a coordinator failure leaves participants holding locks, and across service boundaries a saga with compensating actions is the usual answer instead.

### Aurora Global Database
**Short:** Aurora feature replicating a cluster across AWS regions with sub-second lag and fast cross-region failover.
**Kind:** tech
**Lang:** *
**Roles:** data-access/replication-ha-and-backup @1, data-stores/relational @2, platform-delivery/cloud-platform-and-cost @3

A primary Aurora cluster in one region is paired with read-only secondary clusters in others, and replication happens in the storage layer rather than the database engine: the primary's storage service ships log records to each secondary region over a dedicated path, so the writer spends no CPU on it and lag is typically under a second. Secondaries serve local reads and can be promoted.

Two promotion modes matter. Managed planned failover keeps the topology and loses nothing but needs a healthy primary; the unplanned detach-and-promote path is the disaster case and can lose the last few seconds of writes, since replication is asynchronous. Reach for it for cross-region disaster recovery and low-latency local reads — it is not a multi-region write architecture.

### Automerge
**Short:** CRDT library for local-first apps: concurrent edits merge automatically without a central coordinator.
**Kind:** tech
**Lang:** js, rust
**Roles:** data-access/transactions-and-consistency @1, data-stores/key-value-and-embedded @3

A document is a JSON-like tree in which every change is recorded as an operation with a unique id and its causal dependencies, so two peers that edited offline can exchange histories and both arrive at the same document without a server deciding the order. Text is a sequence CRDT, so concurrent edits to the same paragraph interleave sensibly instead of one overwriting the other, and changes travel as compact binary blobs over any transport you like.

Reach for it for local-first and collaborative editing, where a client must stay writable with no network. The cost is history: the operation log grows with every keystroke and needs compaction, and convergence guarantees no conflict, not that the merged result is what a human intended — application invariants still have to be checked after a merge.

### AWS Backup
**Short:** AWS service applying one backup and retention policy across RDS, DynamoDB, EBS, EFS and other services.
**Kind:** tech
**Lang:** *
**Roles:** data-access/replication-ha-and-backup @1, platform-delivery/cloud-platform-and-cost @3

It is a control plane rather than a new backup mechanism. Backup plans define schedule, lifecycle and retention, resources are selected by tag or ARN, and AWS Backup then drives each service's own snapshot API on your behalf, landing the results in a vault. Vaults carry their own access policy and can be locked in compliance mode so that not even an administrator can shorten retention, and copies can be pushed cross-region and cross-account.

Reach for it when backup policy has to be provable across many services and accounts instead of configured per resource. It does not cover everything — service support varies, and application-consistent database backups may still need the engine's own tooling — and restore is per resource, so rehearse it rather than trusting a green job.

### AWS Elastic Disaster Recovery
**Short:** AWS service continuously replicating whole servers block-level into AWS so they relaunch seconds after a disaster.
**Kind:** tech
**Lang:** *
**Roles:** data-access/replication-ha-and-backup @1, platform-delivery/cloud-platform-and-cost @3

An agent on the source server continuously replicates block-level changes into a low-cost staging area in your AWS account, where lightweight instances and cheap volumes hold the copy; nothing full-sized runs until you launch. Recovery converts those staged volumes into real instances, and because replication is continuous the recovery point is seconds rather than the hours a nightly snapshot gives you.

Reach for it to lift physical, VMware or other-cloud servers into AWS after a disaster, or as a low-friction migration path. Bandwidth and the staging footprint are the ongoing cost, and the number that matters is not the advertised recovery point but a rehearsed recovery time, so run non-disruptive drill launches into an isolated VPC on a schedule.

### AWS RDS Automated
**Short:** RDS/Aurora managed backups giving point-in-time recovery with up to 35 days of retention.
**Kind:** tech
**Lang:** *
**Roles:** data-access/replication-ha-and-backup @1, platform-delivery/cloud-platform-and-cost @3

RDS and Aurora combine a daily storage-level snapshot with continuous archiving of the transaction log, and a restore picks a snapshot and replays log up to the second you name — which is why point-in-time recovery always creates a new instance or cluster rather than rewinding the existing one. Retention runs from one to 35 days, and the backup window is a preference, not an outage, since snapshots are taken at the storage layer.

The trap is deletion: automated backups are tied to the instance's lifetime and disappear with it unless you took a manual snapshot or retained them explicitly. For retention beyond 35 days, cross-region copies, or one policy spanning several services, drive manual snapshots or AWS Backup instead.

### AWS RDS Proxy
**Short:** Managed connection pooler in front of RDS/Aurora that multiplexes many short-lived client connections.
**Kind:** tech
**Lang:** *
**Roles:** data-access/drivers-and-connection-pooling @1, platform-delivery/cloud-platform-and-cost @3

It terminates client connections and multiplexes them onto a much smaller set of real database connections, pinning a backend to a client only while a transaction or a session-scoped feature is in flight — the same transaction-pooling idea as PgBouncer, delivered as a managed multi-AZ service. It also holds credentials in Secrets Manager, supports IAM authentication, and can hold a request briefly during a failover instead of returning an error.

Reach for it in front of Lambda or any fleet that opens far more connections than the instance class can hold. The costs are a per-vCPU hourly charge, an extra network hop, and pinning: session state such as `SET`, temporary tables or server-side prepared statements forces a connection to stay dedicated and quietly destroys the multiplexing you paid for.

### Barman
**Short:** PostgreSQL backup and recovery manager handling WAL archiving, retention policy and point-in-time restore.
**Kind:** tech
**Lang:** *
**Roles:** data-access/replication-ha-and-backup @1

Barman runs on a separate backup host and either pulls from PostgreSQL or receives from it: base backups over rsync or the streaming protocol, and WAL either through an `archive_command` or a persistent `pg_receivewal` stream, which is what keeps the recovery point at the current segment rather than the last completed one. It owns the catalogue, retention policy and consistency checks, so `barman check`, `barman backup` and `barman recover` are most of the operator interface.

Reach for it when you want a dedicated PostgreSQL backup server with rsync-based incremental backups and a clear catalogue of what exists. pgBackRest is the usual alternative and is stronger on parallelism and native object-storage targets, so the choice often comes down to whether backups live on a filesystem you own or in S3.

### Bitronix
**Short:** Standalone JTA/XA transaction manager for two-phase commit across multiple JDBC and JMS resources.
**Kind:** tech
**Lang:** java
**Roles:** data-access/transactions-and-consistency @1

Bitronix Transaction Manager implements JTA as an embeddable library: you register XA datasources and JMS connection factories with it, and it drives prepare and commit across them while journaling each transaction's decision to disk logs so an in-doubt branch can be resolved after a crash. Its appeal was running outside an application server, in a plain JVM or a Spring application.

Reach for it only where you already depend on it. Narayana and Atomikos are the mainstream JTA choices now, and the deeper point is that XA fits containers badly — the transaction log must outlive the process, and a stalled coordinator holds locks on every participant. Across service boundaries, a saga with explicit compensating actions is the pattern that survives.

### c3p0
**Short:** Older JDBC connection pool with statement caching; largely superseded by HikariCP in modern Java stacks.
**Kind:** tech
**Lang:** java
**Roles:** data-access/drivers-and-connection-pooling @1

It predates the modern pools and shows it: acquisition, testing and expiry are governed by a large set of tunables such as `minPoolSize`, `acquireIncrement` and `idleConnectionTestPeriod`, helper threads do the work asynchronously, and it caches `PreparedStatement` objects per connection. Hibernate shipped a c3p0 integration for years, which is why it turns up in so many older Java stacks.

There is no reason to pick it for new work — HikariCP is faster, has far fewer knobs, and is Spring Boot's default. Keep c3p0 only where a legacy application depends on its configuration, and if you inherit one, confirm a validation query or test-on-checkout is configured, since a pool handing out connections the database closed hours ago is the classic failure.

### citext
**Short:** PostgreSQL extension providing a case-insensitive text type, so a unique email column can stay a real constraint.
**Kind:** tech
**Lang:** *
**Roles:** data-access/schema-and-migration @1, runtime-systems/text-encoding-and-regex @2, data-stores/relational @3

The extension registers a text type whose comparison and hashing operators fold case using the database's collation, so `=`, `LIKE`, joins, indexes and — the reason people install it — a `UNIQUE` constraint all behave case-insensitively without every query remembering `lower()`. The value is stored exactly as written, so the original casing survives for display.

The alternative worth knowing is a unique index on the expression `lower(email)`, which needs no extension and is what many teams use; PostgreSQL also supports nondeterministic ICU collations that achieve the same at column level. Choose citext when you want the behaviour attached to the type so no future query can bypass it, and accept that folding is per-character and imperfect in some locales.

### DBCP2
**Short:** Apache Commons JDBC connection pool, the older alternative to HikariCP in Java applications.
**Kind:** tech
**Lang:** java
**Roles:** data-access/drivers-and-connection-pooling @1

Commons DBCP 2 is a JDBC pool built on Commons Pool 2: a borrowed connection is wrapped in a proxy that returns the physical connection on `close()`, with eviction threads, validation queries and an optional `PreparedStatement` cache configured through a wide property set. Tomcat historically shipped a variant of it, which is why it appears in so many servlet deployments.

For new applications HikariCP is the better default — smaller, faster, and what Spring Boot configures unless you exclude it. Keep DBCP2 where a container or legacy application already wires it, and if you do, set `testOnBorrow` with a validation query or enable `testWhileIdle`, because the default is to hand out whatever is in the pool and let the query fail against a connection the server already dropped.

### Django ORM
**Short:** Django's active-record ORM: model classes built by the ModelBase metaclass, querysets and migrations.
**Kind:** tech
**Lang:** python
**Roles:** data-access/orm-and-data-mapping @1, data-access/schema-and-migration @2, runtime-systems/runtime-internals-and-types @3

Model classes are assembled by a metaclass that turns declared fields into descriptors and registers the model with an app registry, so one declaration produces the table, the admin, the forms and the migrations. A `QuerySet` is lazy — it builds a SQL expression and executes only on iteration, slicing or `len()` — and each instance carries its own row, which is the active-record part: `save()` writes the object it belongs to.

The performance traps follow from laziness. Touching a related object inside a loop issues one query per row unless you asked for `select_related`, which joins, or `prefetch_related`, which issues a second query; `.all()` on a large table materialises everything. Use `only`, `defer`, `iterator()` and `annotate` to keep work in the database, and drop to raw SQL when the query is the product.

### DynamoDB Global Tables
**Short:** Multi-region active-active DynamoDB replication with sub-second lag and last-writer-wins conflict resolution.
**Kind:** tech
**Lang:** *
**Roles:** data-access/replication-ha-and-backup @1, data-stores/key-value-and-embedded @2

Each participating region holds a full replica and accepts writes locally, and DynamoDB Streams carry every change to the other regions where it is applied asynchronously — so a write is acknowledged before it has left its home region. Concurrent writes to the same item in different regions are resolved last-writer-wins on a reconciled timestamp, and the loser is discarded silently rather than surfaced as a conflict.

Reach for it when users are spread across regions and you want local write latency plus a warm standby with no failover procedure. Design around the conflict rule: partition ownership by region, or model updates as commutative counters and appends, because anything needing read-modify-write across regions will lose data. Strongly consistent reads remain local to one region.

### etcd
**Short:** Raft-backed distributed key-value store for cluster state, service discovery, leader election and locking.
**Kind:** tech
**Lang:** *
**Roles:** data-access/transactions-and-consistency @1, data-stores/key-value-and-embedded @1, traffic-edge/service-mesh-and-discovery @2, platform-delivery/kubernetes-and-orchestration @3

A cluster of three or five members runs Raft: one leader, and a write is acknowledged only once a majority has persisted it, so the cluster tolerates a minority failing and refuses writes rather than diverging when it loses quorum. Reads are linearizable by default through a ReadIndex round trip, with serializable local reads available when you prefer speed. Keys are versioned by a global revision with watch streams that can replay from any past revision, and leases plus compare-and-swap transactions are what distributed locks and leader election are built from.

It holds all Kubernetes cluster state, which is why its disk fsync latency, not CPU, is usually what decides whether a cluster feels healthy. Reach for it for coordination, service registration, and small config or metadata; it is not a general-purpose database — keep values small, watch the total data size, and defragment and snapshot on a schedule.

### Flyway
**Short:** Versioned SQL schema migration tool that applies ordered scripts and records them in a history table.
**Kind:** tech
**Lang:** *
**Roles:** data-access/schema-and-migration @1

Migrations are ordered SQL files applied once each in version order and recorded in a schema-history table with a checksum, so editing a script that has already run is detected and the migration fails instead of silently letting environments diverge. It executes plain SQL, which means you write the DDL your database actually supports rather than an abstraction over it, and repeatable scripts re-run whenever their checksum changes — the usual home for views and stored procedures.

Wire it into application startup or the deploy pipeline so schema and code ship together. Note that it orders migrations but does not make them safe: a zero-downtime rename is still your job to split into expand-and-contract steps.

### Flyway Teams/Enterprise
**Short:** Paid Flyway tiers adding undo migrations, schema drift detection and dry-run scripting to DB migrations.
**Kind:** tech
**Lang:** *
**Roles:** data-access/schema-and-migration @1

These are commercially licensed tiers on the same engine, and the additions are operational rather than syntactic: `U__` undo scripts paired with a versioned migration, a dry-run mode that writes out the SQL a migration would execute so a DBA can review it first, drift detection comparing a live schema against the changelog, wider database-engine coverage, and richer CI integration.

Weigh them against the discipline they replace. An undo script that has never been rehearsed against production data is a hypothesis, and expand-and-contract migrations — add, deploy, backfill, remove later — leave nothing that needs rolling back. Buy the tiers for dry-run review and engine coverage; do not buy them as a substitute for a forward-only migration habit.

### gh-ost
**Short:** GitHub's triggerless online schema-change tool for MySQL: ALTER large tables without blocking writes.
**Kind:** tech
**Lang:** *
**Roles:** data-access/schema-and-migration @1, data-stores/relational @3

Instead of triggers, it creates a shadow copy of the table, copies rows into it, and applies concurrent changes by connecting as a replica and tailing the binlog, finishing with an atomic rename. Because that apply is asynchronous and outside the writing transaction, gh-ost can throttle or pause itself on replica lag, load or a manual flag -- something a trigger-based tool cannot do, since its work happens inside your writes.

Reach for it for a large ALTER on a busy MySQL table that must stay online. It requires row-based binary logging, a suitable unique key, and no foreign keys pointing at the table, and the cutover is a brief lock, so schedule it rather than assume it is invisible.

### go-redis
**Short:** The de facto Go client for Redis and Valkey, covering cluster, sentinel, pipelining and context-aware commands.
**Kind:** tech
**Lang:** go
**Roles:** data-access/drivers-and-connection-pooling @1, caching/distributed-cache @2

One package covers the standalone, sentinel, cluster and ring topologies behind a common interface, with a built-in connection pool, context deadlines on every call, pipelines and transactions, script helpers that fall back from a hash to the source when the server has forgotten it, and hooks for tracing and metrics.

Reach for it as the default in Go. Two things to get right: give every call a context with a real deadline, since the pool will otherwise happily block, and size the pool against the server rather than the application, because a large fleet multiplying its default pool size is a common way to exhaust a Redis connection limit.

### hashicorp/raft
**Short:** HashiCorp's battle-tested Go implementation of the Raft consensus protocol for replicated state machines.
**Kind:** tech
**Lang:** go
**Roles:** data-access/transactions-and-consistency @1

The same library under its Go import path, and it is worth knowing what rests on it: Consul's catalog and KV, Vault's integrated storage, and Nomad's scheduler state are all replicated state machines built here, which is why those products want three or five servers and refuse writes once they lose quorum. Because the log store is disk-backed, every committed entry costs an fsync, so write latency tracks the slowest majority disk far more than CPU.

If you are choosing rather than inheriting, decide first whether you need consensus in-process at all. Running etcd and reading from it is far less code than owning an FSM, snapshots, restore and membership changes; take the library only when the replicated thing is genuinely your own state and an extra cluster is unacceptable.

### Hibernate 7.x
**Short:** The reference JPA 3.2 ORM provider: persistence-context management, SQL generation, lazy loading and caching.
**Kind:** tech
**Lang:** java
**Roles:** data-access/orm-and-data-mapping @1, caching/in-process-cache @3, data-access/drivers-and-connection-pooling @3

The persistence context is the thing to understand. Inside a transaction an `EntityManager` acts as an identity map, holding managed entities, remembering their loaded state, and flushing the differences as `UPDATE` statements at commit or before a query that could be affected — you rarely call an update method yourself. Lazy associations are proxies fetched on first access, which is where both `LazyInitializationException` outside a session and the N+1 select problem come from.

Fix N+1 with a join fetch, an entity graph or batch fetching, and read the generated SQL rather than trusting the mapping. Version 7 targets Jakarta Persistence 3.2 and a modern Java baseline, so migrating a `javax.persistence` codebase starts as a package rename. For read-heavy reporting queries, jOOQ or plain SQL remains the better tool.

### Hibernate Envers
**Short:** Hibernate module that records an audit revision history of @Audited entities and lets you query past states.
**Kind:** tech
**Lang:** java
**Roles:** data-access/orm-and-data-mapping @1, security/privacy-and-compliance @3

Annotating an entity `@Audited` makes Envers register listeners on Hibernate's flush events. Each transaction that touches an audited entity writes one row to a revision table and a copy of the changed entity into a parallel table suffixed `_AUD`, tagged with the revision number and whether it was an add, modify or delete. `AuditReader` then queries history: the state at a revision, the state at a date, or every revision in which a property changed.

Reach for it when the audit trail is about entity state and every writer goes through Hibernate. Its limits are real — bulk JPQL or native SQL bypasses the listeners entirely and is invisible, the audit tables roughly double write volume and grow without bound unless pruned, and every schema change must be applied twice. A change-data-capture stream off the database log catches everything instead.

### HikariCP
**Short:** Fastest JDBC connection pool and the Spring Boot default; its pool size is the real DB concurrency limit.
**Kind:** tech
**Lang:** java
**Roles:** data-access/drivers-and-connection-pooling @1, runtime-systems/concurrency-and-async @3

A pool keeps physical connections open so a request pays a borrow rather than a TCP connect plus authentication handshake, and HikariCP is fast because it does very little: a lock-free bag of connections and a proxy layer trimmed at the bytecode level. Spring Boot uses it by default with `maximum-pool-size` 10.

That number is the real ceiling on concurrent database work: the eleventh caller blocks inside `getConnection()` and, after `connection-timeout` (30 seconds by default), gets an exception rather than waiting forever. Bigger is usually not better, since a database serves a modest number of concurrent queries efficiently and thrashes past that point — the pool is deliberately a queue, and under virtual threads it is often the last thing still applying backpressure. Turn on `leak-detection-threshold` outside production to find the path that borrows a connection and never closes it.

### JDBC

### JTA
**Short:** Jakarta Transactions: the Java standard API for XA two-phase commit across multiple resource managers.
**Kind:** spec
**Lang:** java
**Roles:** data-access/transactions-and-consistency @1

The specification defines a boundary between three roles: application code demarcates through `UserTransaction` or a container annotation, a transaction manager coordinates, and each resource exposes an `XAResource` the coordinator can prepare, commit or roll back. ### Lettuce
**Short:** Netty-based, thread-safe async/reactive Redis client for the JVM; Spring Boot's default Redis driver.

### Liquibase
**Short:** Database schema change management using versioned XML/YAML/JSON/SQL changelogs with rollback and drift detection.

**Lang:** *
**Roles:** data-access/schema-and-migration @1

### Narayana
**Short:** Red Hat JTA/XA transaction manager providing 2PC across resources; ships a Spring Boot starter.

### Patroni
**Short:** PostgreSQL HA template that runs automatic leader election and failover using etcd, Consul or ZooKeeper as the DCS.
**Kind:** tech
**Lang:** *
**Roles:** data-access/replication-ha-and-backup @1, data-access/transactions-and-consistency @3

Patroni is a daemon that runs alongside each PostgreSQL instance and turns a set of them into a cluster with exactly one primary. Leadership is a key with a TTL in a distributed configuration store — etcd, Consul, ZooKeeper or Kubernetes objects — that the current leader must keep renewing; if it cannot, the key expires and the healthy replicas race to promote one. Split-brain is prevented by the store's own consensus, not by PostgreSQL, which is why the DCS needs its own quorum of nodes.

### Paxos
**Short:** The classic consensus protocol letting a replica set agree on a value despite crashes; the ancestor of Raft and friends.
**Kind:** concept
**Lang:** *
**Roles:** data-access/transactions-and-consistency @1

A proposer picks a ballot number and asks a majority of acceptors to promise not to accept anything older. If any of them has already accepted a value, the proposer must re-propose that value instead of its own, and only then asks the majority to accept it. Those two rules are the whole safety argument: any two majorities intersect, so a value that could have been chosen can never be contradicted by a later ballot. Liveness is not guaranteed — two proposers can duel indefinitely — which is why real systems elect a distinguished leader.

Single-decree Paxos agrees one value; Multi-Paxos runs it repeatedly to build a replicated log, which is what Chubby and Spanner do. Raft rearranged the same guarantees around an explicit leader and log-matching rules precisely because Paxos is notoriously hard to implement correctly, so for new work, implement Raft.

### Percona XtraBackup

**Kind:** tech
**Lang:** *
**Roles:** data-access/replication-ha-and-backup @1

It copies InnoDB's data files while the server keeps taking traffic, recording the redo log generated during the copy, and then replays that log against the copied files to reach a single consistent point — the "prepare" step. Because the result is a physical copy rather than a stream of SQL statements, restoring a large database is dramatically faster than replaying a `mysqldump`, and combined with binary logs it gives point-in-time recovery. The details that bite: non-InnoDB tables such as MyISAM still need a brief lock to be copied consistently, and the tool version must match the server version family. Neither is a reason to avoid it, but both are reasons to rehearse a restore rather than trusting a green backup job.

**Roles:** data-access/schema-and-migration @1, data-stores/relational @3, data-stores/time-series @3

PostgreSQL gives you declarative partitioning but will not create tomorrow's partition for you, and inserting a row with no matching partition is an error. This extension closes that gap: you register a parent table with an interval and a premake count, and its maintenance routine creates future child partitions ahead of time and detaches or drops ones past the retention window.

Reach for it for time-ordered data such as events, audit trails and metrics, where the real win is that expiring old data becomes an instant DROP of a child table rather than a long DELETE that bloats the heap. The operational requirement is that maintenance actually runs on a schedule, via its background worker or pg_cron, otherwise you silently run out of partitions.

### pg_repack
**Short:** PostgreSQL extension that rebuilds bloated tables and indexes online without an exclusive lock.
**Kind:** tech
**Lang:** *
**Roles:** data-access/schema-and-migration @1, data-stores/relational @3, data-access/replication-ha-and-backup @3

MVCC leaves dead tuples behind, and autovacuum reclaims that space for reuse without returning it to the filesystem, so a table that churned heavily stays large; `VACUUM FULL` compacts it but holds an `ACCESS EXCLUSIVE` lock throughout. pg_repack instead builds a new copy in the background, captures concurrent changes through a trigger into a log table, applies them, and swaps the files, taking a brief exclusive lock only at the start and the end.

Reach for it to reclaim disk after a bulk delete or a spell of bloat, or to rebuild indexes and re-cluster a table online. Plan for it: it needs free space for a full second copy of the table and its indexes, the table needs a primary key or a unique not-null index, and an interrupted run leaves temporary objects to clean up.

### pg_uuidv7 extension
**Short:** PostgreSQL extension generating time-ordered UUIDv7 keys on versions where the function is not yet built in.
**Kind:** tech
**Lang:** *
**Roles:** data-access/schema-and-migration @1, data-stores/relational @3

The extension supplies the generator function and helpers on server versions that do not yet have one built in. A v7 UUID is 48 bits of Unix millisecond timestamp followed by random bits, so values generated over time sort in roughly insertion order under an ordinary byte comparison — which is all a B-tree needs to keep new rows landing together.

That matters because a random v4 key scatters inserts across the whole index, dirtying pages everywhere and destroying cache locality, while a time-ordered key appends near the right edge as a sequence does. Reach for it when you need client-generatable, non-guessable keys without that write amplification. Newer PostgreSQL releases ship `uuidv7()` natively, so check first and drop the extension on upgrade, and remember the embedded timestamp discloses creation time.

### PgBouncer
**Short:** Lightweight PostgreSQL connection pooler/proxy with session, transaction and statement pooling modes.
**Kind:** tech
**Lang:** *
**Roles:** data-access/drivers-and-connection-pooling @1, traffic-edge/proxy-and-load-balancer @3, data-access/replication-ha-and-backup @3

The pooling mode is the entire decision. Session mode holds a server connection for the client's whole session and saves almost nothing. Transaction mode - the usual choice - returns the server connection at COMMIT, which is what collapses thousands of application connections onto a few dozen Postgres backends, at the cost of breaking anything that spans transactions: session-level `SET`, advisory locks held across statements, `LISTEN`/`NOTIFY`, temporary tables, and server-side prepared statements unless prepared-statement support is explicitly configured.

Reach for it whenever the application tier scales horizontally, because a Postgres backend is an OS process with real per-connection memory: connection count, not query volume, is often what falls over first. ### pgpool-II
**Short:** Older PostgreSQL middleware combining connection pooling with load-balanced read routing and failover management.
**Kind:** tech
**Lang:** *
**Roles:** data-access/drivers-and-connection-pooling @1, data-access/replication-ha-and-backup @2, traffic-edge/proxy-and-load-balancer @3

It is several things in one process: a connection pool, a query-parsing proxy that sends writes to the primary and spreads reads across replicas, a watchdog giving the pgpool layer itself high availability with a virtual IP, and optional failover scripting for the PostgreSQL cluster beneath. That breadth is the tradeoff. Parsing-based routing is heuristic and surprises people — a read inside a transaction, a function with side effects, a session variable — and one component doing pooling, routing and failover fails in more ways than one doing pooling alone. ### pt-online-schema-change

**Roles:** data-access/schema-and-migration @1, data-access/replication-ha-and-backup @3

### QueryDSL

### R2DBC
**Short:** Reactive relational database API for the JVM: non-blocking, backpressure-aware SQL access for WebFlux.
**Kind:** spec
**Lang:** java
**Roles:** data-access/drivers-and-connection-pooling @1, runtime-systems/concurrency-and-async @2

The specification defines a small set of reactive interfaces — `ConnectionFactory`, `Connection`, `Statement`, `Result` — whose methods return a `Publisher`, so a query becomes a stream that honours backpressure: rows arrive as the subscriber requests them and no thread is parked waiting on the network. ### r2dbc-postgresql, r2dbc-mysql
**Short:** The R2DBC driver implementations for PostgreSQL and MySQL, giving WebFlux non-blocking SQL access.
**Kind:** tech
**Lang:** java
**Roles:** data-access/drivers-and-connection-pooling @1, runtime-systems/concurrency-and-async @3

These are the concrete drivers behind the specification. ### Raft
**Short:** Leader-based consensus algorithm for replicating a log across a quorum; the basis of etcd, Consul and KRaft.
**Kind:** concept
**Lang:** *
**Roles:** data-access/transactions-and-consistency @1, data-access/replication-ha-and-backup @2

Raft splits consensus into three understandable pieces. Leader election: nodes use randomized election timeouts, and a candidate that wins a majority vote for a term becomes leader, with terms giving a monotonic ordering that lets a stale leader be recognised and stood down. Log replication: only the leader appends client entries and pushes them to followers, and an entry commits once a majority has persisted it. Safety: a candidate cannot win unless its log is at least as up to date as the voters', so a committed entry survives every future election.

The consequences are what to remember in a design: an odd cluster of three or five, a majority required so the cluster stops rather than diverges, an fsync on a majority of disks per commit, and reads that need a leader lease or an extra round trip to be linearizable.

### RDS cross-region read replica
**Short:** An RDS read replica in another AWS region, giving cross-region DR with seconds-to-minutes of replication lag.
**Kind:** tech
**Lang:** *
**Roles:** data-access/replication-ha-and-backup @1, platform-delivery/cloud-platform-and-cost @3

For the engine-native services this is ordinary asynchronous replication with the network stretched: the source ships its binary log or WAL to an RDS instance in another region, which replays it. Lag therefore depends on write volume and the link, usually seconds but capable of growing to minutes under load. The replica is readable, and promoting it makes it an independent writable instance that stops receiving changes.

Reach for it as a low-effort disaster-recovery target and for reads near users in another region. Aurora Global Database replicates in the storage layer and is stronger wherever it applies.

### Reaper
**Short:** Scheduler and UI that runs and tracks Cassandra anti-entropy repairs segment by segment so they finish inside gc_grace.
**Kind:** tech
**Lang:** *
**Roles:** data-access/replication-ha-and-backup @1, data-stores/wide-column @2

Cassandra needs anti-entropy repair to reconcile replicas and, critically, to run on every table within `gc_grace_seconds`, or deleted data can resurrect when a tombstone expires before every replica has seen it. A full `nodetool repair` on a large cluster is a long, heavy, all-or-nothing operation. ### Redis Sentinel

Sentinel is a separate set of processes, not a Redis mode. The starter is a dependency aggregate plus the auto-configuration it triggers. The defaults deserve attention before production. `spring.jpa.hibernate.ddl-auto` should be `validate`, with Flyway or Liquibase owning the schema and never `update`. Open-session-in-view is on unless you disable it, which holds a connection for the whole request and lets lazy loading happen in the view layer. And `show-sql` is no substitute for logging the generated SQL with bound parameters at debug level.

### Spring Data JDBC
**Short:** Lightweight Spring persistence: repositories with no lazy loading or dirty tracking, so SQL stays predictable.
**Kind:** tech
**Lang:** java
**Roles:** data-access/orm-and-data-mapping @1, data-access/drivers-and-connection-pooling @3

It is a deliberately simpler persistence model than JPA: an aggregate root and the objects it owns are loaded and saved as a unit, with no persistence context, no lazy loading, no dirty checking and no proxies. A save issues its statements immediately, and because there is no first-level cache, loading the same row twice gives two objects — which is the point, since the SQL a call produces is predictable from reading the code.

Reach for it when the domain follows DDD aggregates and you want repositories without JPA's lifecycle surprises. What you give up is exactly what JPA sells: no automatic many-to-many, no lazy references between aggregates, and cross-aggregate relationships are ids you resolve yourself. For a graph-shaped model with heavy reuse JPA still fits better, and for read models plain `JdbcClient` is simpler still.

### Spring Data JPA 4.x
**Short:** Spring's JPA repository layer with derived queries, projections, paging and auditing over Hibernate.
**Kind:** tech
**Lang:** java
**Roles:** data-access/orm-and-data-mapping @1, data-stores/relational @3

The repository interface is the mechanism: declare one extending `JpaRepository` and Spring generates a proxy at startup, deriving queries from method names, honouring `@Query` where a name would be absurd, and supporting projections, paging, sorting, `@EntityGraph` fetch plans and auditing. Everything underneath is still Hibernate and a persistence context, so JPA's semantics — flush timing, lazy loading, cascade rules — apply unchanged.

The things that bite are inherited from JPA rather than caused by this layer: a derived method that walks a lazy association is N+1, a paged query with a fetch join paginates in memory, and `@Transactional(readOnly = true)` matters more than it looks. Use projections to avoid loading entities you only read, and check the emitted SQL rather than trusting method names to do the right thing.

### Spring Data MongoDB
**Short:** Spring's object-document mapper for MongoDB: repositories, MongoTemplate, derived queries and aggregation support.
**Kind:** tech
**Lang:** java
**Roles:** data-access/orm-and-data-mapping @1, data-stores/document @2, data-access/drivers-and-connection-pooling @3

It offers two levels over the MongoDB Java driver. Repositories derive finder methods from names and accept `@Query` with raw JSON filters, while `MongoTemplate` is the imperative escape hatch covering the aggregation pipeline, bulk operations, find-and-modify and index management. A mapping layer converts documents to and from your classes, driven by `@Document`, `@Field`, `@Id` and `@Indexed`, with custom converters where the default guess is wrong.

The judgement call is index creation: building indexes automatically from annotations is convenient in development and dangerous in production, where a build can block the collection, so declare them through migrations instead. And treat the aggregation pipeline as first class — a lot of code that fetches documents and folds them in Java should be one server-side grouping stage.

### Spring Data MongoDB 4.x
**Short:** Spring's MongoDB module: repository interfaces, MongoTemplate, aggregation pipeline support and index management.
**Kind:** tech
**Lang:** java
**Roles:** data-access/orm-and-data-mapping @1, data-stores/document @2

The same module at the version line aligned with Spring Framework 6 and Boot 3: Jakarta package names, a modern Java baseline, and the current MongoDB driver underneath, with support for the aggregation pipeline, multi-document transactions on a replica set, sharded documents, and Atlas features such as vector search exposed through the template.

In practice you spend your time on three decisions. Repositories or `MongoTemplate` — derived methods for simple lookups, template for anything with an aggregation or an update operator. ### Spring Data R2DBC
**Short:** Reactive repository abstraction over R2DBC drivers, giving non-blocking access to relational databases.
**Kind:** tech
**Lang:** java
**Roles:** data-access/orm-and-data-mapping @1, data-access/drivers-and-connection-pooling @2, runtime-systems/concurrency-and-async @3

R2DBC is the non-blocking counterpart to JDBC, and this module puts the familiar repository derivation on top of it, so a `ReactiveCrudRepository` returns `Mono` and `Flux` instead of entities and lists. ### Spring JDBC
**Short:** Spring's JdbcTemplate/JdbcClient layer removing JDBC boilerplate and translating SQL exceptions into one hierarchy.
**Kind:** tech
**Lang:** java
**Roles:** data-access/orm-and-data-mapping @1, data-access/drivers-and-connection-pooling @2

`JdbcTemplate` and the newer fluent `JdbcClient` handle the mechanical part of JDBC — take a connection from the `DataSource`, create and bind the statement, iterate the result set, close everything in the right order even on failure — leaving you the SQL and a row mapper. Named parameters, batch updates, generated-key handling and an exception translator that maps vendor error codes onto Spring's `DataAccessException` hierarchy make up the rest of the surface.

Reach for it when you want to write the SQL with nothing between you and the database: reporting queries, bulk operations, read models. It participates in `@Transactional` alongside JPA because both go through the same transaction manager, so mixing them in one transaction is fine as long as you understand when Hibernate flushes.

### Spring JdbcTemplate
**Short:** Spring's JDBC facade: one call replaces acquire/execute/release and converts SQLException to unchecked types.
**Kind:** tech
**Lang:** java
**Roles:** data-access/orm-and-data-mapping @1, apis-frameworks/design-patterns-and-principles @2

The classic form of that layer: one call replaces the acquire-execute-map-close sequence, with `query`, `queryForObject`, `update` and `batchUpdate` taking SQL, a varargs parameter list and a `RowMapper`. Connections come from the `DataSource` through a transaction-aware holder, so the template joins an existing `@Transactional` transaction instead of opening its own, and every `SQLException` is translated into the unchecked `DataAccessException` hierarchy.

It is still perfectly good code and is thread-safe once constructed, so one instance per repository is normal. For new work `JdbcClient` wraps the same engine in a fluent API that removes positional-parameter guessing and reads better, and for bulk loads prefer `batchUpdate` with a sensible batch size over a loop of single updates — the round trips, not the SQL, are the cost.

### Spring TX 7.x
**Short:** Spring's transaction abstraction: PlatformTransactionManager, TransactionTemplate and @Transactional proxies.
**Kind:** tech
**Lang:** java
**Roles:** data-access/transactions-and-consistency @1, apis-frameworks/aop-middleware-and-scheduling @2, data-access/orm-and-data-mapping @3

The abstraction has three parts. `PlatformTransactionManager` and its reactive sibling form the SPI implemented per resource — for a plain `DataSource`, for JPA, for JTA — so demarcation code never names JDBC or Hibernate. `TransactionTemplate` is the programmatic form. `@Transactional` is the declarative one, implemented by an AOP proxy that begins a transaction before the method and commits or rolls back after, driven by propagation, isolation, timeout, read-only and rollback rules.

The proxy is where the surprises live: calling one method of a bean from another method of the same bean bypasses the proxy entirely and runs with no transaction, and by default only unchecked exceptions roll back, so a caught-and-logged exception commits partial work. `REQUIRES_NEW` really does take a second connection, which is how a pool of ten deadlocks under load.

### SQLAlchemy
**Short:** Python ORM and SQL toolkit; 2.0 Mapped[] models, Session as Unit of Work, and async engines for ASGI apps.
**Kind:** tech
**Lang:** python
**Roles:** data-access/orm-and-data-mapping @1, data-access/drivers-and-connection-pooling @2, apis-frameworks/design-patterns-and-principles @3

It is two layers. Core builds SQL expressions against table metadata and can be used entirely without objects; the ORM maps classes onto those tables and keeps a `Session` that acts as an identity map and unit of work, accumulating changes and flushing them in dependency order at commit. Understanding the flush-and-expire cycle prevents most of the confusing bugs: attributes are expired at commit and silently re-query on next access, and iterating a lazy relationship in a loop is the N+1 problem unless you ask for `selectinload` or `joinedload`.

Async support is the same API through `AsyncSession` with an async driver such as asyncpg, with lazy loading deliberately disallowed because it would require implicit IO - relationships must be eager-loaded explicitly. Alembic generates migrations by diffing the same metadata, so schema and models stay one source of truth.

### sqlalchemy[asyncio]
**Short:** SQLAlchemy with its asyncio extra: async engine, session and connection pooling over async drivers.
**Kind:** tech
**Lang:** python
**Roles:** data-access/orm-and-data-mapping @1, data-access/drivers-and-connection-pooling @2, devtools/testing-and-mocking @3

The extra pulls in greenlet, which is what actually makes async SQLAlchemy work: the ORM's internals are ordinary blocking code, and rather than rewrite them, SQLAlchemy runs them inside a greenlet and switches out to the event loop wherever the driver would block. ### uuidv7
**Short:** RFC 9562 time-ordered UUID: globally unique but sorted by creation time, so B-tree keys stop fragmenting.
**Kind:** spec
**Lang:** *
**Roles:** data-access/schema-and-migration @1, data-stores/relational @2

The layout is what makes it useful: 48 bits of Unix epoch milliseconds in the most significant position, then version and variant bits and the remaining bits random, optionally with a sub-millisecond counter for monotonicity inside one millisecond. Because the timestamp leads, values generated over time compare in roughly creation order under a plain byte comparison, which is all a B-tree needs.

That matters at the storage layer. A v4 key is uniformly random, so every insert lands on a different leaf page, the working set becomes the whole index, and in a clustered index such as InnoDB's it causes page splits and write amplification. A v7 key appends near the right-hand edge like a sequence while staying independently generatable — though it does disclose creation time, which is occasionally a reason to keep v4.

### WAL-G
**Short:** Backup tool that archives PostgreSQL WAL and base backups to object storage for compressed PITR restore.
**Kind:** tech
**Lang:** *
**Roles:** data-access/replication-ha-and-backup @1

WAL-G is wired in as PostgreSQL's archive command, so each completed WAL segment is compressed and shipped to object storage as it is produced, while periodic base backups — optionally deltas against the previous one — give the starting point that a restore replays from. ### ZAB
**Short:** ZooKeeper Atomic Broadcast: the leader-based total-order consensus protocol keeping ZooKeeper replicas identical.
**Kind:** concept
**Lang:** *
**Roles:** data-access/transactions-and-consistency @1

ZooKeeper Atomic Broadcast is not Paxos. It is a primary-backup protocol built around a total order of transactions identified by a `zxid` whose high bits are the leader epoch and low bits a counter within it. A leader is elected by a quorum, synchronises followers to its history, then broadcasts each write as a two-phase proposal — propose, quorum acknowledges, commit — with the guarantee ZooKeeper's semantics depend on: state changes are applied in exactly the order the leader issued them, and a new leader never drops a transaction a previous one committed.

That prefix-ordering property is what lets ZooKeeper offer FIFO client order and linearizable writes, which locks and leader election are built from. It is worth knowing because the guarantee is much stronger than eventual agreement, and because ordering every write through one leader is also what bounds throughput.

### ZooKeeper
**Short:** Zab-based coordination service for leader election, config, locks and service discovery in distributed systems.
**Kind:** tech
**Lang:** *
**Roles:** data-access/transactions-and-consistency @1, traffic-edge/service-mesh-and-discovery @2, data-movement/event-streaming-and-processing @3, data-access/replication-ha-and-backup @3

ZooKeeper exposes a small, strongly consistent hierarchical namespace of znodes replicated by the Zab protocol across an odd-sized ensemble, with writes going through the leader and needing a quorum. The useful primitives fall out of two features — ephemeral nodes that vanish when a session's heartbeats stop, and sequential nodes combined with watches — which together give leader election, distributed locks, membership and configuration every participant agrees on.

It is for coordination metadata, not data: small values, low write rate, high durability requirements. Newer systems increasingly embed the same consensus in-process with Raft instead of depending on a separate ensemble — Kafka's KRaft mode is the well-known case — so a new design should ask whether it really wants another cluster to operate.
