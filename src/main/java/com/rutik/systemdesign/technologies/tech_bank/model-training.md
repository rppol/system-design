### accelerate
**Short:** Hugging Face wrapper that runs the same training loop on CPU/multi-GPU/TPU over DDP, FSDP or DeepSpeed.
**Kind:** tech
**Lang:** python
**Roles:** model-training/distributed-training @1, gpu/multi-gpu-and-collectives @3

You keep your own PyTorch training loop and let `Accelerator()` prepare the model, optimizer, scheduler, and dataloaders; the same script then runs on CPU, a single GPU, multi-GPU DDP, FSDP, DeepSpeed, or TPU depending on an `accelerate config` file and `accelerate launch` flags, with no `if distributed` branches, no manual `.to(device)`, and no hand-written sampler sharding. Mixed precision, gradient accumulation, and gradient clipping are flags on the same object.

It also handles loading a model too large for one GPU by sharding it across devices and CPU or disk offload. Reach for it when you want distributed training without adopting a whole framework or rewriting your loop as a Trainer subclass — it is the layer underneath the `transformers` Trainer and most diffusion training scripts, so understanding it explains their behaviour too.

### Adan
**Short:** Adaptive Nesterov momentum optimizer (Xie et al. 2022) reporting faster convergence than Adam on vision and NLP.
**Kind:** concept
**Lang:** *
**Roles:** model-training/deep-learning-framework @1

Adan reformulates Nesterov's look-ahead so it can be computed from gradients you already have: alongside the usual moving averages of the gradient and its square, it tracks a moving average of the difference between consecutive gradients and uses that term as a correction approximating the look-ahead gradient, with no second forward or backward pass. The update that results is in the decoupled-weight-decay mould of AdamW with one extra curvature-aware term.

Reach for it when a run is learning-rate sensitive and you can afford a third optimizer buffer, since it keeps one more state tensor per parameter than Adam and that memory is rarely free on a large model. Reported gains are workload dependent, so treat it as an experiment against a properly tuned AdamW baseline rather than a drop-in win; AdamW is what nearly every published recipe and piece of tuning folklore assumes.

### AdapterHub
**Short:** Hub and library for sharing and composing pretrained adapters (language + task) over a frozen base model.
**Kind:** tech
**Lang:** python
**Roles:** model-training/fine-tuning-and-peft @1

The library injects small bottleneck modules between the layers of a frozen pretrained transformer and trains only those, so a task costs a few megabytes of weights instead of a full checkpoint. Its distinguishing idea is composition: adapters are named, shareable artifacts you load onto a base model by identifier, then stack, fuse or average, so a language adapter and a task adapter combine to reach a language-task pair neither was trained on. LoRA and prefix tuning sit behind the same interface.

Reach for it when you want that composition machinery, or when a published adapter already exists for your base model. For an ordinary single-task LoRA fine-tune, `peft` is the mainstream choice, with broader model coverage and tighter integration into the rest of the training and serving stack.

### Alpaca-Cleaned
**Short:** Quality-filtered version of the 52K-example Alpaca instruction dataset, used for supervised fine-tuning.
**Kind:** dataset
**Lang:** *
**Roles:** model-training/fine-tuning-and-peft @1, ml-lifecycle/labeling-and-synthetic-data @2

The original set was generated by prompting a strong model with self-instruct, and it carried the defects that implies: hallucinated answers, prompts referring to an input that was never supplied, empty outputs, wrong arithmetic, and refusals learned from the generator rather than warranted by the request. The cleaned release fixes or removes those examples while keeping the same instruction, input and output schema, so it drops into any script that reads the original.

Use it as a cheap end-to-end smoke test that a fine-tuning pipeline actually works, or as the starting point for a first instruction tune. It is single-turn, English and modest in size, so a model trained only on it plateaus quickly; for real instruction quality you want a larger curated mixture with multi-turn conversations in it.

### Apache Spark MLlib
**Short:** Spark's distributed machine-learning library: pipelines, classical models and ALS recommenders over cluster-scale data.
**Kind:** tech
**Lang:** *
**Roles:** model-training/classical-ml-and-boosting @1, data-movement/batch-and-distributed-compute @2, applied-ml/recommenders-and-graph-ml @2

It is the machine-learning package inside Spark, built on the DataFrame API: `Transformer` and `Estimator` stages compose into a `Pipeline` in the scikit-learn shape, and every stage executes as a distributed Spark job, so features and labels never leave the cluster. The algorithm set is the one that parallelizes cleanly -- linear and logistic regression, decision trees and gradient-boosted trees, k-means, ALS matrix factorization -- with `CrossValidator` for tuning.

Reach for it when the training data already lives in Spark and is too large to collect onto one machine, which is really the only strong reason to use it. The algorithm menu is narrow and per-model quality generally trails a dedicated boosting library, so when a representative sample fits in memory it is usually better to aggregate in Spark and train in XGBoost or LightGBM.

### AutoGluon
**Short:** AutoML library that trains and stack-ensembles a portfolio of tabular, text and vision models from presets.
**Kind:** tech
**Lang:** python
**Roles:** model-training/classical-ml-and-boosting @1, ml-lifecycle/experiment-tracking-and-tuning @2

You hand `TabularPredictor` a DataFrame and a label column and it does the rest: infers column types, builds features, trains a portfolio of models -- LightGBM, XGBoost, CatBoost, random forests, a neural network, nearest neighbours -- and combines them with multi-layer stacking, where each layer's out-of-fold predictions become features for the next, finishing in a weighted ensemble. Presets trade quality against a wall-clock budget it actually respects.

Reach for it to get a strong tabular baseline from one call, or to find out how much headroom a hand-tuned model really has. The cost is a large, slow ensemble that is awkward to explain and to deploy; where latency or interpretability matters, take its leaderboard as evidence and ship a single tuned model instead.

### AWS SageMaker Training
**Short:** Managed training jobs on ephemeral AWS clusters, with the SageMaker model-parallel and data-parallel libraries.
**Kind:** tech
**Lang:** *
**Roles:** model-training/distributed-training @1, ml-lifecycle/ml-platform-and-pipelines @2, platform-delivery/cloud-platform-and-cost @3

A training job is a container image, an entry point, an instance type and count, and S3 paths for input and output. SageMaker provisions the cluster, streams data in through file, pipe or fast-file mode, runs the job and tears the instances down, so you pay only for the duration; checkpoints written to S3 mean a spot-interrupted job resumes rather than restarts. Distributed runs use its data-parallel and model-parallel libraries or plain `torchrun`.

Reach for it when you want ephemeral GPU capacity without operating a cluster, and especially for managed spot training, where the savings are large and the interruption handling is done for you. The costs are a per-hour premium over raw EC2, container startup time that dominates short jobs, and a fair amount of AWS-specific wiring that follows your code around.

### Axolotl
**Short:** YAML-configured LLM fine-tuning framework covering continued pretraining, SFT, LoRA and QLoRA.
**Kind:** tech
**Lang:** python
**Roles:** model-training/fine-tuning-and-peft @1, model-training/alignment-and-rl @3

The whole run lives in one YAML file: base model, dataset paths and format, whether this is continued pretraining or SFT, LoRA/QLoRA rank and target modules, sequence length and sample packing, and the DeepSpeed or FSDP config for multi-GPU. It wraps `transformers`, `peft`, and `trl` underneath, so you get their behaviour without writing a training loop, and the config file itself becomes the reproducibility record.

Its practical advantage is dataset flexibility — it understands a range of instruction and chat formats and applies the model's chat template for you, which is where hand-rolled fine-tunes most often go wrong. Reach for it when you want a repeatable fine-tune from a config; drop to `trl` or plain PyTorch when you need a custom loss, a nonstandard data pipeline, or RL-style training it does not express.

### CatBoost
**Short:** Gradient-boosted decision trees with ordered boosting and native categorical handling; strong on tabular data.
**Kind:** tech
**Lang:** python
**Roles:** model-training/classical-ml-and-boosting @1

Its signature idea is ordered target statistics: to encode a categorical value it uses only the rows preceding that one in a random permutation, so the encoding for a row never sees that row's own target. That is what stops the target leakage plain mean-encoding produces, and it is why you pass raw category columns through `cat_features` with no manual encoding step and no leakage-prone preprocessing to get wrong. Ordered boosting applies the same permutation trick to the gradient estimates.

Its trees are symmetric — every node at a given depth splits on the same feature and threshold — which acts as a regularizer and makes inference very fast, since scoring becomes an index computation rather than a branchy walk; missing values, text and embedding features are handled natively too. Reach for it first on tabular data with high-cardinality categoricals; LightGBM often trains faster on wide numeric data, and comparing the two is cheap enough to be worth doing.

### category_encoders
**Short:** sklearn-compatible encoders for high-cardinality categoricals: CatBoost, James-Stein, M-estimate, binary, base-N and hashing.
**Kind:** tech
**Lang:** python
**Roles:** model-training/classical-ml-and-boosting @1, ml-lifecycle/ml-platform-and-pipelines @3

It is a set of scikit-learn transformers for turning high-cardinality categorical columns into numbers without one-hot's width explosion: target, CatBoost, James-Stein and M-estimate encoders replace a category with a smoothed statistic of the target, while binary, base-N and hashing encoders compress the identity into a few columns. All follow the `fit`/`transform` contract and accept DataFrames, so they drop straight into a `Pipeline` and a `ColumnTransformer`. The trap is leakage -- any target-based encoding computed on rows that also train the model lets the label leak into a feature, and this library's `TargetEncoder` smooths with a sigmoid weighted by `min_samples_leaf` and does not cross-fit, so wrap it in a fold-aware wrapper such as `NestedCVWrapper` or fit it separately inside each CV fold. Reach for it when a categorical has thousands of levels and you want an encoder scikit-learn does not ship -- CatBoost, James-Stein, M-estimate, base-N or hashing. For plain target encoding scikit-learn's own `TargetEncoder` is now the safer default, since it cross-fits internally; and for a handful of levels one-hot is simpler than either.

### CleanRL
**Short:** Single-file, dependency-light reference implementations of RL algorithms, aimed at learning not production.
**Kind:** tech
**Lang:** python
**Roles:** model-training/alignment-and-rl @1

Each algorithm is one self-contained file -- PPO in a few hundred lines including environment setup, network, update and logging -- with no shared base classes or abstraction layers to trace through. That is a deliberate inversion of usual library design: you read the whole algorithm top to bottom and modify it by editing your copy rather than subclassing anything. Runs log to TensorBoard and Weights & Biases, and the project publishes benchmarked results so a file's behaviour is a known quantity.

Reach for it to learn how an algorithm actually works, to reproduce a published baseline, or as the starting point for a research variant. The cost is exactly the duplication it embraces: a change you want in five algorithms is five edits, so a production system maintaining many agents is better served by a structured library such as Stable-Baselines3 or TorchRL.

### composer
**Short:** MosaicML's PyTorch training library packaging speed-up recipes, batch-size ramping and run monitoring callbacks.
**Kind:** tech
**Lang:** python
**Roles:** model-training/deep-learning-framework @1, model-training/distributed-training @2, ml-lifecycle/experiment-tracking-and-tuning @3

Composer is a PyTorch trainer whose distinguishing feature is a library of speed-up algorithms -- progressive resizing, selective backpropagation, label smoothing, layer freezing, blurpool, sequence-length warmup -- switched on as objects passed to the `Trainer` and inserted at the right points in the loop by an event-based callback system. The same trainer owns mixed precision, gradient accumulation, FSDP or DeepSpeed sharding, deterministic resumption and streaming datasets read from object storage.

Reach for it when wall-clock cost per run is what you are optimizing and you want those recipes without implementing them, or when you are already inside the MosaicML and Databricks stack, where it is the loop underneath llm-foundry. For an ordinary fine-tune, PyTorch Lightning or the Hugging Face Trainer carry far more community answers and integrations.

### cuML
**Short:** RAPIDS GPU-accelerated scikit-learn-compatible ML library: k-means, PCA, UMAP and forests at 10-100x speedups.
**Kind:** tech
**Lang:** python
**Roles:** model-training/classical-ml-and-boosting @1, gpu/gpu-math-libraries @2

cuML re-implements the classical scikit-learn algorithms as CUDA kernels over GPU-resident data -- k-means, DBSCAN, PCA and truncated SVD, UMAP and t-SNE, nearest neighbours, random forests, linear and logistic regression, SVM -- behind the same `fit`, `predict` and `transform` interface. It accepts cuDF DataFrames, CuPy arrays and NumPy alike and interoperates with the rest of RAPIDS, so an ETL pipeline can stay on the GPU from load to model.

The wins are largest where cost is dominated by distance or matrix work, which is why UMAP, t-SNE and nearest-neighbour search are the usual reasons to install it. Coverage is a subset of scikit-learn and some parameters behave differently or are unimplemented, so check the specific algorithm rather than assuming a drop-in swap; on small datasets, transfer and launch overhead can leave the CPU ahead.

### DeepSpeed
**Short:** PyTorch training library whose ZeRO sharding and CPU/NVMe offload fit models too large for one GPU's memory.
**Kind:** tech
**Lang:** python
**Roles:** model-training/distributed-training @1, model-training/deep-learning-framework @3

ZeRO removes the redundancy in data-parallel training by partitioning optimizer state across ranks at stage 1, gradients as well at stage 2, and the parameters themselves at stage 3, gathering each shard only when needed. That trades extra communication for memory, and the offload options push optimizer state or parameters to CPU RAM or NVMe when even the sharded copy will not fit.

Reach for it when the model does not fit the GPUs you have. PyTorch's own FSDP now covers much of the stage-3 ground natively, so the reasons to pick DeepSpeed specifically are the offload tiers, pipeline parallelism and its fused kernels.

### DeepSpeed ZeRO
**Short:** DeepSpeed's ZeRO optimizer sharding states, gradients and parameters across ranks to fit larger training jobs.
**Kind:** tech
**Lang:** python
**Roles:** model-training/distributed-training @1, model-training/fine-tuning-and-peft @2

ZeRO is the memory-partitioning scheme inside DeepSpeed, enabled by a JSON config stanza rather than a code change. Stage 1 splits optimizer state across ranks, stage 2 adds the gradients, stage 3 adds the parameters themselves, all-gathering each layer's weights just before use and discarding them straight after. The saving grows with world size and each stage buys it with more communication, so the right stage is the lowest one that fits.

Stage 3 combined with optimizer or parameter offload to CPU or NVMe is what lets a model far larger than aggregate GPU memory train at all, at a throughput cost that can be severe. Reach for it when memory rather than speed is the binding constraint; when the model already fits, plain data parallelism is faster, and PyTorch's FSDP now covers most of the stage-3 ground natively.

### Distillation
**Short:** Training a small student model on a large teacher's outputs to keep most of the quality at a fraction of the cost.
**Kind:** concept
**Lang:** *
**Roles:** model-training/fine-tuning-and-peft @1, inference/quantization-and-compression @2

The student is trained not on hard labels but on the teacher's full output distribution, which carries far more information per example -- the relative probabilities assigned to the wrong classes encode similarity structure a one-hot label throws away. A temperature term softens both distributions so those small probabilities matter, and the loss usually mixes the soft-target term with the ordinary label term. Variants also match intermediate hidden states or attention maps, and for generative models the teacher simply writes the training data.

Reach for it when a large model already works and the problem is serving cost or latency, since a distilled student can hold most of the quality at a fraction of the parameters. It inherits the teacher's mistakes and biases with no independent signal to correct them, and it needs a large unlabelled corpus in the right distribution; where the quality ceiling matters more than the cost, quantization degrades accuracy far less.

### DoRA
**Short:** Weight-decomposed low-rank adaptation: splits LoRA updates into magnitude and direction for better quality per rank.
**Kind:** concept
**Lang:** *
**Roles:** model-training/fine-tuning-and-peft @1

DoRA starts from the observation that a full fine-tune changes a weight matrix's magnitude and its direction in ways a plain low-rank update reproduces poorly. It therefore decomposes each pretrained weight into a per-column magnitude vector and a normalized direction matrix, trains the magnitude directly, and applies the low-rank update only to the direction before renormalizing. The extra trainable parameters amount to one vector per matrix, so it stays parameter-efficient.

It typically closes part of the gap to full fine-tuning at low rank, which makes it worth trying when a rank-8 or rank-16 LoRA is underfitting and raising the rank is expensive. It costs extra compute in the forward pass because of the normalization, and it is exposed as a flag on an existing LoRA config in `peft`, so the experiment is cheap; where LoRA already matches full fine-tuning there is nothing to gain.

### einops
**Short:** Readable tensor rearrangement: rearrange, reduce and repeat expressions replace error-prone reshape/permute chains.
**Kind:** tech
**Lang:** python
**Roles:** model-training/deep-learning-framework @1, runtime-systems/collections-and-algorithms @3

Instead of a `reshape` and a `permute` whose axis order you have to reconstruct mentally, you write the transformation as an equation over named axes, and patch extraction or head splitting becomes one readable line with the block sizes named as keyword arguments. `reduce` and `repeat` cover pooling and broadcasting the same way, `einsum` handles contractions, and `Rearrange` is a layer you drop into a `Sequential`. The same notation works across PyTorch, JAX, TensorFlow and NumPy.

The real value is verification rather than brevity: the axis names are checked against the actual tensor at runtime, so a wrong dimension order raises immediately instead of silently training a broken model, which is the classic attention-head reshaping bug. Reach for it anywhere shapes get non-trivial. It adds a small parsing overhead in a very hot loop, and a reader who does not know the notation will find it opaque.

### ElasticNet
**Short:** Linear regression regularized by a mix of L1 and L2 penalties, combining lasso sparsity with ridge stability.
**Kind:** concept
**Lang:** *
**Roles:** model-training/classical-ml-and-boosting @1

The penalty is a weighted sum of the L1 and L2 norms of the coefficient vector, controlled by an overall strength and a mixing ratio, so at one extreme it is lasso and at the other ridge. The L1 part drives coefficients to exactly zero and performs selection; the L2 part fixes lasso's failure on correlated predictors, where lasso keeps one member of a correlated group essentially at random and zeroes the rest. With both terms, correlated features enter and leave together.

Reach for it when you have many predictors, expect most to be irrelevant, and know the survivors are correlated with each other -- which describes most genomics, text and sensor feature sets. Both hyperparameters need cross-validation, and coefficients are biased toward zero, so read them as a ranking rather than as effect sizes. Where interpretability is not the goal, gradient boosting almost always predicts better.

### Flower
**Short:** Framework-agnostic federated learning framework: FedAvg/FedProx/FedAdam strategies with PyTorch, TF or JAX clients.
**Kind:** tech
**Lang:** python
**Roles:** model-training/distributed-training @1, security/privacy-and-compliance @2

Flower splits a federated run into a server holding a `Strategy` and clients implementing `fit` and `evaluate` over their own local data; the two exchange only parameter arrays over gRPC, so the framework has no opinion about what runs inside a client. That is what makes it framework-agnostic, with PyTorch on one silo and TensorFlow on another perfectly legal, and the `Strategy` object is where aggregation lives -- FedAvg, FedProx, FedAdam or your own subclass. A simulation mode runs many virtual clients on one machine.

Reach for it for research and for cross-device or cross-silo setups where the raw data genuinely cannot move. Be clear that federation alone is not privacy: updates leak information, so secure aggregation or differential privacy has to be added deliberately. Statistical heterogeneity between clients and stragglers are the real problems, and both are harder than the plumbing Flower solves.

### FSDP
**Short:** PyTorch-native ZeRO-3 sharding of parameters, gradients and optimizer state across GPUs; FSDP2 shards per parameter.
**Kind:** tech
**Lang:** python
**Roles:** model-training/distributed-training @1, model-training/deep-learning-framework @3, runtime-systems/memory-processes-and-os @3

Parameters, gradients and optimizer state are sharded across ranks; a unit's full parameters are all-gathered just before its forward and backward and freed immediately after, so peak memory falls roughly with world size in exchange for extra communication. That trade is what makes a model too large for one GPU trainable at all, and it is why the wrapping granularity matters: wrap too coarsely and the peak barely moves, too finely and the collectives dominate the step.

FSDP2 (`fully_shard`) applies bottom-up per transformer block and represents each shard as a DTensor, which lets it compose with tensor or pipeline parallelism, `torch.compile` and per-parameter mixed precision instead of fighting them. In practice it is paired with activation checkpointing and bf16, and the first thing to check when throughput disappoints is whether communication is overlapping with compute.

### GitHub Code
**Short:** Large multi-language public code corpus used for continued pretraining of code-focused models.
**Kind:** dataset
**Lang:** *
**Roles:** model-training/fine-tuning-and-peft @1

It is a bulk extract of source files from public GitHub repositories, distributed as a streamable dataset with one record per file carrying the code, its path, repository, detected language and license. Filtering happens at load time, so you select the languages and licenses you intend to train on rather than downloading everything, which matters because the raw corpus is measured in terabytes.

Use it for continued pretraining or for building a code-specific tokenizer, where sheer volume is the point. Treat the license field as the first thing you handle rather than an afterthought, and expect real effort on cleaning: near-duplicate files are rampant across forks and vendored directories, generated and minified files teach nothing, and leaked credentials and benchmark solutions both need removing before the corpus contaminates your evaluation.

### GPT-NeoX
**Short:** EleutherAI's GPU training framework for pretraining large autoregressive models with 3D parallelism.
**Kind:** tech
**Lang:** python
**Roles:** model-training/distributed-training @1, model-training/fine-tuning-and-peft @2

It began as a fork of Megatron-LM and DeepSpeed and is maintained as a pretraining codebase in its own right: one YAML configuration describes the model, tokenizer, data mixture and parallelism grid, and the launcher spreads the run across nodes using tensor, pipeline and data parallelism with ZeRO underneath. Data is pretokenized into indexed binary files so loading never bottlenecks the GPUs, and checkpoints convert to the Hugging Face format for downstream use.

It was the code behind an openly released 20B model and several later open model suites, so its configs double as reproducible recipes at a scale most groups never publish. Reach for it if you are genuinely pretraining from scratch on a GPU cluster and want a tested configuration to start from; for fine-tuning, or anything that fits on one node, it is far more machinery than the job requires.

### GPyTorch
**Short:** GPU-accelerated Gaussian process library on PyTorch, used for calibrated uncertainty and Bayesian optimization.
**Kind:** tech
**Lang:** python
**Roles:** model-training/classical-ml-and-boosting @1, applied-ml/interpretability-fairness-and-causal @2, model-training/deep-learning-framework @3

A Gaussian process returns a posterior distribution over functions rather than a point prediction, but the exact computation involves inverting a kernel matrix that grows with the square of the dataset. GPyTorch never forms that inverse: it solves the linear systems iteratively with conjugate gradients and estimates log-determinants stochastically, expressing everything as matrix-vector products that run on a GPU through PyTorch autograd. Kernels, means and likelihoods are modules, so a deep kernel is just a network feeding a GP layer.

Reach for it when you need calibrated uncertainty from limited data -- Bayesian optimization and hyperparameter search, active learning, surrogates for expensive simulations -- and note that BoTorch builds the acquisition-function layer on top of it. Even with iterative solvers the cost grows steeply with data, so large problems move to sparse inducing-point or variational approximations, and for big tabular prediction a boosted tree with conformal intervals is far cheaper.

### Gymnasium
**Short:** The standard RL environment API and reference environments (CartPole, Atari, MuJoCo); successor to OpenAI Gym.
**Kind:** tech
**Lang:** python
**Roles:** model-training/alignment-and-rl @1

The contract is deliberately tiny: `reset()` returns an observation and an info dict, `step(action)` returns the next observation, the reward, a terminated flag, a truncated flag and info, and `observation_space` and `action_space` describe the shapes. Separating termination from truncation is the correctness fix that motivated the rename, because bootstrapping the value function is right on a time-limit truncation and wrong on a real terminal state. Wrappers compose observation, reward and action transforms, and vector environments batch many copies.

Reach for it as the interface every RL library already speaks -- implement it for your own simulator and Stable-Baselines3, Tianshou, RLlib and CleanRL all work unchanged. It is a specification plus reference environments, not an algorithm library, and the classic control and locomotion tasks it ships are benchmarks rather than anything resembling a real problem.

### HDBSCAN
**Short:** Hierarchical density-based clustering finding variable-density clusters and labelling noise; no eps to tune.
**Kind:** tech
**Lang:** python
**Roles:** model-training/classical-ml-and-boosting @1, applied-ml/timeseries-and-anomaly @3

It builds a minimum spanning tree over a mutual-reachability distance that pushes sparse points apart, condenses the resulting hierarchy, and selects the clusters that persist across the widest range of density thresholds. That last step is what removes DBSCAN's `eps` parameter: instead of one global density cut, each cluster is extracted at whatever density suits it, so a tight cluster and a diffuse one are both found in the same run. Points that never join a persistent cluster are labelled noise.

Reach for it when the cluster count is unknown, clusters are not spherical, and the data genuinely contains outliers -- embedding spaces and topic discovery over a UMAP projection are the standard pairing. `min_cluster_size` is the main knob and it materially changes the answer, so tune it deliberately. It scales worse than k-means on very large data, and in high dimensions reduce first, because distances stop discriminating.

### HelpSteer2
**Short:** NVIDIA's human preference dataset with multi-attribute ratings, used to train reward models for RLHF.
**Kind:** dataset
**Lang:** *
**Roles:** model-training/alignment-and-rl @1, ml-lifecycle/evaluation-and-benchmarks @3

Rather than a single preferred and rejected pair, each response carries separate numeric ratings on several attributes -- helpfulness, correctness, coherence, complexity and verbosity -- collected from human annotators. Training a reward model to predict those attribute scores instead of one scalar gives a signal you can inspect and reweight, and lets you deliberately stop rewarding length, which is the classic way a preference-trained model degenerates.

It is permissively licensed, which is the practical reason it gets used: much preference data is either proprietary or derived from another vendor's model in ways that restrict commercial training. Reach for it to train or evaluate a reward model without a licensing argument. It is comparatively small and English-only, so treat it as one component of a data mixture rather than a complete alignment set.

### higher
**Short:** PyTorch library making nn.Modules differentiable through their own optimizer steps, for meta-gradients.
**Kind:** tech
**Lang:** python
**Roles:** model-training/fine-tuning-and-peft @1, model-training/deep-learning-framework @2

Ordinary PyTorch optimizers update parameters in place, which severs the autograd graph and makes it impossible to differentiate through a training step. This library produces a functional, stateless copy of a module whose parameters are ordinary tensors, plus a differentiable optimizer that returns new parameters rather than mutating old ones, so an inner loop of gradient steps stays inside a single graph and an outer loss can be backpropagated all the way through it.

That is exactly what MAML-style meta-learning, learned optimizers and differentiable hyperparameter tuning need. The cost is memory, since every inner step's activations and parameter copies are retained, which is why unrolled step counts stay small and first-order approximations get used instead. `torch.func`, with `functional_call` and `grad`, now offers the same capability inside the core library, and that is where new code should start.

### Horovod
**Short:** Uber's framework-agnostic ring-all-reduce library for data-parallel training across GPUs and hosts.
**Kind:** tech
**Lang:** python
**Roles:** model-training/distributed-training @1, gpu/multi-gpu-and-collectives @2

It was designed so that a single-GPU training script becomes distributed with a handful of lines: initialize, pin the process to a GPU by local rank, shard the dataset, broadcast the initial variables so every worker starts identical, and wrap the optimizer so gradients are averaged before the update. The averaging uses ring all-reduce over NCCL or MPI, where each worker exchanges only with its neighbours, so bandwidth per worker stays constant as the cluster grows instead of converging on one parameter server. Launch is through its own runner or through mpirun.

Reach for it for TensorFlow, or for a shop running more than one framework that wants a single distribution layer. For PyTorch specifically, distributed data parallel is native, uses the same collectives underneath, and is what most current code and documentation assume.

### Hugging Face Trainer

### JAX
**Short:** Functional array framework with composable grad/vmap/jit transforms, XLA-compiled to GPU and TPU.
**Kind:** tech
**Lang:** python
**Roles:** model-training/deep-learning-framework @1, inference/compiler-and-runtime-optimization @2, gpu/kernel-programming @3

It is the NumPy API plus composable function transformations: `grad` differentiates a pure function, `vmap` adds a batch dimension without rewriting the code, `jit` compiles it through XLA, and `pmap` or `shard_map` spread it across devices. The functional constraint is real, since arrays are immutable, state is threaded explicitly and randomness takes an explicit key, and that is both what makes the transformations composable and reproducible and what makes the code feel foreign coming from PyTorch. ### JAX/Flax
**Short:** Google's functional array framework with jit/grad/vmap and XLA compilation, plus Flax layers; TPU-native.
**Kind:** tech
**Lang:** python
**Roles:** model-training/deep-learning-framework @1, model-training/distributed-training @2, inference/compiler-and-runtime-optimization @3

Flax supplies the neural-network layer JAX deliberately omits. A module declares submodules and calls them but holds no weights: `init` returns a parameter pytree and `apply` takes it as an explicit argument, which keeps the model a pure function that `jit`, `grad` and `vmap` can transform. Optimizer state comes from Optax, and both pytrees are threaded through the training step by hand -- verbose next to PyTorch, and the reason a compiled step is fully deterministic and shardable.

Reach for it on TPUs, where XLA is the native compilation path, and for large-scale work where explicit device meshes give precise control over how a model is split. Against that, pretrained checkpoints, tutorials and third-party libraries overwhelmingly target PyTorch, so you spend time porting, and error messages from inside a traced function take practice to read.

### Lasso
**Short:** L1-regularized linear regression that shrinks coefficients to exactly zero, giving built-in feature selection.
**Kind:** concept
**Lang:** *
**Roles:** model-training/classical-ml-and-boosting @1

Adding the sum of the absolute values of the coefficients to the squared-error loss produces a constraint region with corners on the axes, and the optimum lands on a corner far more often than not -- which is why coefficients reach exactly zero rather than merely small, unlike the ridge penalty. Fitting is by coordinate descent, and sweeping the penalty strength traces a regularization path along which features enter the model one at a time.

Reach for it when you want a sparse, readable model out of many candidate predictors, or as a feature-selection step before something else. Two limits matter: with correlated predictors it keeps one and drops the rest essentially arbitrarily, which makes the selection unstable across resamples, and it cannot select more features than you have observations. Elastic net fixes both by mixing in an L2 term.

### LibMTL
**Short:** PyTorch multi-task learning library implementing GradNorm, DWA, PCGrad, CAGrad and MGDA loss balancing.
**Kind:** tech
**Lang:** python
**Roles:** model-training/deep-learning-framework @1

Training one network on several tasks fails in a specific way: per-task gradients have different magnitudes and can point in conflicting directions, so a naive sum of losses lets one task dominate and quietly degrade the rest. LibMTL implements the published fixes behind one interface -- weighting schemes such as GradNorm, uncertainty weighting and DWA that rescale each task's contribution, and gradient-surgery methods such as PCGrad, CAGrad and MGDA that project or recombine conflicting gradients before the update.

Reach for it when comparing balancing strategies on a shared-encoder model, since implementing five of them correctly is genuinely fiddly and the benchmarks it ships make the comparison honest. For two or three closely related tasks, tuned static loss weights are often just as good and far simpler; the sophisticated methods earn their keep as task count and conflict grow.

### libsvm
**Short:** The C++ support vector machine library underneath scikit-learn's SVC; used directly for custom kernels.
**Kind:** tech
**Lang:** cpp, python
**Roles:** model-training/classical-ml-and-boosting @1

It is the C++ implementation of support vector classification and regression that most other tooling wraps, solving the dual quadratic program by sequential minimal optimization -- decomposing it into two-variable subproblems with a closed-form solution. It supports linear, polynomial, RBF and sigmoid kernels plus precomputed kernel matrices, one-class SVM for novelty detection, and Platt scaling for probability estimates, and it defines the sparse text format many datasets are still distributed in.

### LightGBM MPI
**Short:** LightGBM's MPI build, splitting gradient-boosted tree training across machines by feature or data parallelism.
**Kind:** tech
**Lang:** *
**Roles:** model-training/classical-ml-and-boosting @1, model-training/distributed-training @2

### LLaMA-Adapter
**Short:** Prefix-style parameter-efficient adaptation for LLaMA, extended to vision-language multimodal tuning.
**Kind:** tech
**Lang:** python
**Roles:** model-training/fine-tuning-and-peft @1, applied-ml/vision-speech-and-multimodal @3

Instead of injecting low-rank matrices into weight matrices, it prepends a small set of learnable prompt vectors to the keys and values of the upper transformer layers and gates their attention contribution with a parameter initialized at zero. ### LM-Cocktail
**Short:** Weight-merging method that blends a domain fine-tune back with the base model to keep general ability.
**Kind:** tech
**Lang:** python
**Roles:** model-training/fine-tuning-and-peft @1, search-retrieval/ann-index-library @3

A domain fine-tune reliably costs general ability, and the fix here is a weighted average of the parameters of the fine-tuned model, the base model and optionally other fine-tunes, computed in weight space with no further training. ### mamba-ssm
**Short:** Reference Mamba/Mamba-2 state-space model implementation with CUDA kernels for the selective parallel scan.
**Kind:** tech
**Lang:** python
**Roles:** model-training/deep-learning-framework @1, gpu/kernel-programming @2

The package implements the selective state-space layer that replaces attention with a recurrence whose state transition depends on the input. Written naively that recurrence is sequential and hopeless on a GPU, so the value here is the hardware-aware kernel: a parallel associative scan that keeps the expanded state in on-chip memory and never materializes it in HBM, plus a fused path for the surrounding projections and gating. Mamba-2 recasts the same computation as a structured matrix multiply that maps onto tensor cores.

The attraction is complexity -- linear in sequence length, with a constant-size state at inference instead of a KV cache growing with every token -- which is why it appeals for very long sequences and for genomics and audio. Against that, a fixed state cannot recall arbitrary earlier tokens the way attention can, so quality on copy and retrieval tasks lags, and most strong published models using it are hybrids keeping a few attention layers.

### Math-Shepherd
**Short:** Process reward model for mathematical reasoning that scores each intermediate step rather than only the final answer.
**Kind:** model
**Lang:** *
**Roles:** model-training/alignment-and-rl @1, ml-lifecycle/evaluation-and-benchmarks @3

The interesting part is where the step labels come from. Rather than paying annotators to mark each line of a solution, it estimates a step's quality automatically: from the prefix up to that step, sample many completions and score the step by how often they reach the correct final answer. ### Megatron-LM
**Short:** NVIDIA's large-scale LLM training framework: tensor, pipeline and sequence parallelism for 70B+ models.
**Kind:** tech
**Lang:** python
**Roles:** model-training/distributed-training @1, gpu/multi-gpu-and-collectives @2, model-training/deep-learning-framework @3, model-training/fine-tuning-and-peft @3

Megatron-LM is NVIDIA's reference implementation of the parallelism strategies that make training beyond a single GPU's memory possible. Tensor parallelism splits the weights of each matrix multiply across GPUs inside a node, where the interconnect is fastest. Reach for it for pretraining and continued pretraining at the scale where a single node is not an option, roughly the 70B-and-above range. **Short:** Ray-based large-scale RLHF framework: PPO, GRPO and REINFORCE++ with vLLM-accelerated rollout generation.
**Kind:** tech
**Lang:** python
**Roles:** model-training/alignment-and-rl @1, model-training/distributed-training @2

The components of an RLHF loop - actor, critic, reward model, reference model and a vLLM engine doing rollout generation - are placed as separate Ray actors, so each can own its own GPUs and the generation step runs at inference-engine speed instead of inside the training framework. Generation is normally the bottleneck in PPO, so that separation is the reason the design exists rather than an implementation detail.

It implements the surrounding recipe too: supervised fine-tuning, reward modeling, DPO, and the on-policy algorithms PPO, GRPO and REINFORCE++. Reach for it when a run outgrows one machine and a single-process trainer stops fitting; for a small model on one node, TRL is dramatically less to configure and operate.

### Optax
**Short:** JAX optimizer library built from composable gradient transformations chained into schedules and clipping.
**Kind:** tech
**Lang:** python
**Roles:** model-training/deep-learning-framework @1

An optimizer here is a gradient transformation: a pair of pure functions that initialize state and map gradients plus state to updates plus new state. Because the interface is uniform, `chain` composes them -- clip by global norm, then scale by Adam's moments, then scale by a schedule, then add weight decay -- and named optimizers such as `adamw` are simply such chains. Schedules are functions of step count, and everything is a pytree, so optimizer state shards exactly as the parameters do.

Reach for it as the standard optimizer layer for any JAX training loop, Flax included. The compositional design is what makes an unusual recipe -- layerwise learning rates, gradient accumulation, a custom preconditioner -- a small amount of code rather than a subclass. The cost is threading optimizer state explicitly through every step, which feels like bookkeeping until you need to shard or checkpoint it.

### Pearl
**Short:** Meta's production RL agent library with contextual bandits, offline RL and safe-exploration components.
**Kind:** tech
**Lang:** python
**Roles:** model-training/alignment-and-rl @1, applied-ml/recommenders-and-graph-ml @3

Pearl composes an agent from replaceable parts -- a policy learner, an exploration module, a replay buffer, a history summarizer, a safety module -- which is a deliberate response to the fact that production decision systems rarely need a textbook algorithm and always need the parts around it. Contextual bandits sit alongside deep RL as first-class citizens, offline RL is supported for learning from logged data, and dynamic action spaces are handled, which matters when the candidate set changes per request.

Reach for it for a recommendation, ranking or notification problem framed as sequential decision-making, where the real questions are exploration under a safety constraint and learning from logged traffic rather than which policy-gradient variant to use. For simulator-based research on standard benchmarks, Stable-Baselines3 or TorchRL have far more published baselines to compare against.

### PEFT
**Short:** HuggingFace library for parameter-efficient fine-tuning: LoRA, QLoRA, prefix and adapter tuning on far less memory.
**Kind:** tech
**Lang:** python
**Roles:** model-training/fine-tuning-and-peft @1

The idea it packages is that a fine-tune's weight change is close to low rank, so you can freeze the pretrained matrices and learn a small pair of factors added alongside them. Memory falls on three axes at once -- no gradients and no optimizer moments for the frozen weights, and only the factors to store -- which is what puts a fine-tune of a multi-billion-parameter model on a single consumer GPU, especially combined with a 4-bit quantized base.

The decisions that matter are which modules to adapt and at what rank: attention projections only is the cheap default and consistently weaker than including the feed-forward projections, while rank trades capacity against overfitting on a small dataset. Reach for it for style, format and domain adaptation. It cannot install knowledge absent from the base model, and it will not fix a task the base model fundamentally cannot do.

### pomegranate
**Short:** Probabilistic modelling library for mixture models, hidden Markov models, Bayesian networks and naive Bayes.
**Kind:** tech
**Lang:** python
**Roles:** model-training/classical-ml-and-boosting @1, applied-ml/timeseries-and-anomaly @3

Models are built compositionally: a distribution is an object, a mixture is a set of distributions with weights, a hidden Markov model is a set of states each holding a distribution, and a Bayesian network is a graph of them, so a mixture of exponential and Poisson components is as easy to express as a Gaussian one. Fitting uses expectation-maximization, and the models tolerate missing data and out-of-core batches. It now sits on PyTorch tensors, which brings GPU execution and autograd along. Reach for it when you want a generative model whose structure and parameters you can read and defend, for anomaly detection or sequence segmentation, rather than the single Gaussian mixture scikit-learn offers.

### Process Reward Models
**Short:** Reward models scoring each reasoning step instead of the final answer, a cheap value signal for search and RL.
**Kind:** concept
**Lang:** *
**Roles:** model-training/alignment-and-rl @1, llm-apps/agent-framework @2, ml-lifecycle/evaluation-and-benchmarks @3

An outcome reward model scores only the finished answer, which gives one bit of feedback for a long chain of reasoning and credits every step equally, including the wrong ones a lucky answer survived. A process reward model instead scores each intermediate step, so a solution can be judged by its weakest link and a search can prune a bad branch before spending tokens on it. Step labels are usually generated automatically, by sampling continuations from each prefix and measuring how often they reach a correct answer.

Reach for one when reasoning is long, verifiable and multi-step -- mathematics, code, tool-use chains -- where the density of the signal justifies the cost of building it. The limits are that the labelling procedure needs a checkable final answer, the model is expensive to run because it scores every step of every candidate, and it learns to reward steps that look like correct reasoning, which is not quite the same thing.

### PyMC
**Short:** Probabilistic programming library for full Bayesian inference via MCMC and variational methods.
**Kind:** tech
**Lang:** python
**Roles:** model-training/classical-ml-and-boosting @1, applied-ml/interpretability-fairness-and-causal @2

In PyMC you write the generative story of your data directly — priors, deterministic transforms, and a likelihood — inside a model context block, and the library compiles that graph, derives gradients, and samples the posterior with NUTS, or approximates it variationally when sampling is too slow. What comes back is a distribution over every parameter rather than a point estimate, so uncertainty, credible intervals and hierarchical partial pooling across groups are first-class rather than bolted on.

Reach for it when data per group is thin and pooling helps, when you need calibrated uncertainty rather than a number, or when domain knowledge deserves to be an explicit prior — small-sample A/B tests, hierarchical forecasting, measurement models. ### PyTorch
**Short:** Tensor and autograd framework with dynamic graphs; the default runtime for training and running deep models on GPU.
**Kind:** tech
**Lang:** python
**Roles:** model-training/deep-learning-framework @1, model-training/distributed-training @3, inference/compiler-and-runtime-optimization @3, runtime-systems/collections-and-algorithms @3

You write ordinary Python and the framework records a tape of the tensor operations that actually executed, so `loss.backward()` differentiates the graph that ran — there is no separate graph-definition phase, which is why a `print` statement or a breakpoint mid-model just works. Tensors carry a device, so `.to("cuda")` moves the work and every operation dispatches a GPU kernel, usually into cuBLAS or cuDNN; `torch.compile` traces and fuses the graph ahead of time to cut kernel-launch and memory-traffic overhead where eager execution leaves performance on the table.

Around that core sit the layers, losses and optimizers in `torch.nn` and `torch.optim`, `DataLoader` with pinned memory and non-blocking copies for feeding the GPU, and `DistributedDataParallel` and FSDP for multi-GPU and multi-node training. It is also the runtime that inference engines such as vLLM build on, which is why their wheels are pinned to a specific PyTorch version. Reach for it as the default for anything neural; for tabular problems a gradient-boosting library is usually both stronger and much cheaper.

### PyTorch DDP
**Short:** PyTorch DistributedDataParallel: one process per GPU, gradients all-reduced via NCCL; the default data-parallel path.
**Kind:** api
**Lang:** python
**Roles:** model-training/distributed-training @1, gpu/multi-gpu-and-collectives @2

### PyTorch FSDP
**Short:** PyTorch fully sharded data parallel: parameters, gradients and optimizer state split across ranks to fit big models.
**Kind:** tech
**Lang:** python
**Roles:** model-training/distributed-training @1, gpu/multi-gpu-and-collectives @2

Where distributed data parallel keeps a full copy of the model on every GPU, this shards the parameters, gradients and optimizer state across ranks, so aggregate memory rather than per-GPU memory sets the model size you can train. Each unit's weights are all-gathered immediately before its forward and backward and freed straight after, and gradients are reduce-scattered instead of all-reduced, which is why communication volume is higher than DDP's for the same step.

Reach for it when the model plus its optimizer state will not fit one GPU; when it does fit, DDP is simply faster. The knobs deciding whether it performs are the wrapping policy, which sets how much is gathered at once, mixed precision, and activation checkpointing. Checkpoint format is the operational trap, since a sharded state dict is not interchangeable with a full one without an explicit conversion.

### PyTorch Lightning
**Short:** Structured training-loop framework over PyTorch: removes boilerplate and plugs in multi-GPU strategies and logging.
**Kind:** tech
**Lang:** python
**Roles:** model-training/deep-learning-framework @1, model-training/distributed-training @2, ml-lifecycle/experiment-tracking-and-tuning @3

You move the model, `training_step`, `validation_step` and optimizer configuration into a LightningModule, and the Trainer owns the loop: device placement, gradient accumulation, mixed precision, checkpointing, early stopping, logging, and the distributed strategy -- DDP, FSDP or DeepSpeed -- selected by a flag rather than by rewriting the script.

Reach for it to stop reimplementing the same loop per project and to go from one GPU to multi-node without touching model code. The cost is indirection: an unusual training scheme -- adversarial, multi-optimizer, custom backward -- fights the hidden loop, and debugging means knowing which hook runs when.

### Ray RLlib
**Short:** Ray's distributed reinforcement learning library: PPO, DQN, SAC and IMPALA scaled across a cluster.
**Kind:** tech
**Lang:** python
**Roles:** model-training/alignment-and-rl @1, applied-ml/recommenders-and-graph-ml @3, model-training/distributed-training @3

RLlib splits an RL run into Ray actors: rollout workers each holding an environment copy and collecting experience, a learner applying the gradient updates, and a replay buffer where the algorithm needs one. Scaling is a config value rather than a code change, because the same algorithm class runs on one process or several hundred, and both synchronous algorithms such as PPO and asynchronous ones such as IMPALA are expressed in that structure. Reach for it when environment simulation is the bottleneck and throwing machines at rollout collection is the fix, or when you need multi-agent or offline RL inside an existing Ray cluster. ### Ray Train
**Short:** Ray's distributed training layer that scales a PyTorch or HF loop across a cluster and handles placement.
**Kind:** tech
**Lang:** python
**Roles:** model-training/distributed-training @1, ml-lifecycle/ml-platform-and-pipelines @2, data-movement/batch-and-distributed-compute @3

You wrap your existing PyTorch, Lightning or Hugging Face training function and hand it to a trainer with a scaling config saying how many workers and whether they want GPUs; Ray places those workers across the cluster, sets up the distributed process group so `DistributedDataParallel` works unchanged, shards a Ray Data stream across them, and reports metrics and checkpoints to shared storage so a failed worker restarts from the last one rather than the beginning.

### Regressor
**Short:** Generic label for a supervised model predicting a continuous value, e.g. scikit-learn's DecisionTreeRegressor.
**Kind:** concept
**Lang:** *
**Roles:** model-training/classical-ml-and-boosting @1

A naming convention more than a thing: a supervised model whose output is a continuous number rather than a class, which in scikit-learn is spelled by the suffix, so every family ships a paired classifier and regressor and the difference is the loss and what `predict` returns. Squared error is the usual default and optimizes the conditional mean, absolute error optimizes the median and resists outliers, and a quantile loss gives you prediction intervals instead of a point.

The practical consequences follow from that choice. Metrics differ from classification -- mean absolute error in the target's own units, root mean squared error when large misses hurt disproportionately, and R-squared only as a relative reference. And tree-based regressors predict a constant within each leaf, so they cannot extrapolate beyond the range they were trained on, which is the trap when the target trends over time.

### Ring Attention
**Short:** Sequence-parallel attention sharding one long sequence across GPUs, rotating KV blocks in a ring to overlap comms.
**Kind:** concept
**Lang:** *
**Roles:** model-training/distributed-training @1, llm-apps/prompting-context-and-structured-output @2, gpu/multi-gpu-and-collectives @3

Attention over a very long sequence is limited by activation memory, not compute, so this splits the sequence itself across devices: each GPU holds one contiguous block of queries, keys and values, computes attention against the block it currently has, then passes its key-value block to the next device in a ring while receiving the previous one. After a full rotation every query has seen every key, and because the send overlaps the local computation, the communication largely disappears behind it.

Reach for it when context length rather than parameter count is what will not fit -- long-document training, video, and the very long context windows a model is extended to. It requires an online, blockwise attention formulation such as flash attention to combine partial results correctly, it needs high-bandwidth interconnect between the ring members, and for a sequence that already fits on one device it is pure overhead.

### RLlib
**Short:** Ray's reinforcement learning library: PPO, DQN, IMPALA and friends scaled across hundreds of rollout workers.
**Kind:** tech
**Lang:** python
**Roles:** model-training/alignment-and-rl @1, model-training/distributed-training @2

The same distributed RL library, referred to by its short name. An algorithm is built from a config object -- environment, framework, rollout and learner resources, hyperparameters -- and then stepped with `train()`, which hides whether the rollout workers are threads on your laptop or processes across a hundred nodes. The catalogue is broad: PPO, DQN and its rainbow-style variants, SAC, IMPALA and APPO, plus offline algorithms that learn from recorded batches.

Its reason to exist is throughput on environments expensive to simulate, and it inherits Ray's fault tolerance and cluster scheduling for free. Weigh that against version churn, since the config and API surface have been reworked across releases and tutorials date quickly, and against the difficulty of debugging a distributed run. Prototype the environment and reward single-process first, then scale here once the problem is right.

### rotary-embedding-torch
**Short:** Small PyTorch package providing a reference rotary position embedding (RoPE) implementation to drop into attention.
**Kind:** tech
**Lang:** python
**Roles:** model-training/deep-learning-framework @1

Rotary position embedding encodes position by rotating pairs of dimensions inside the query and key vectors by an angle proportional to the token index, so the dot product between two tokens depends only on their relative distance. This package supplies that as a small module you apply to queries and keys inside your attention block, with the frequency table cached, plus the common variants -- an XPos flavour, interpolation and frequency scaling for extending context beyond the trained length, and separate handling of two axes for images.

Reach for it when writing an attention implementation yourself and you want a reference that is known correct, because the failure mode of a hand-rolled version is subtle: a wrong dimension pairing or an off-by-one in the position offset during cached decoding trains and generates without error and merely degrades quality. If you are using an existing model implementation it already has this built in and the dependency adds nothing.

### SetFit
**Short:** Few-shot text classification recipe: contrastively fine-tune a sentence embedder, then fit a light classifier head.
**Kind:** tech

### Sophia
**Short:** Second-order optimizer for LLM pretraining that uses a cheap diagonal Hessian estimate to precondition steps.
**Kind:** concept
**Lang:** *
**Roles:** model-training/deep-learning-framework @1

Sophia is a second-order method built to be affordable: it estimates only the diagonal of the Hessian, refreshes that estimate every few dozen steps rather than every step, and uses it as a preconditioner with a clipping term bounding the per-coordinate update. The clipping is what keeps it stable where a raw Newton step would not be, since an inaccurate or near-zero curvature estimate would otherwise produce an enormous step in that direction.

The claim is fewer steps to a given loss than Adam at roughly comparable per-step cost, which if it holds on your workload is a direct saving on a pretraining budget. Treat it as an experiment rather than a default: published gains come from specific language-model pretraining setups, it adds a curvature buffer to optimizer memory, and AdamW is what every reference recipe, schedule and piece of tuning folklore assumes.

### Stable-Baselines3
**Short:** Well-tested PyTorch implementations of PPO, SAC, DQN and friends with a consistent Gym-style API.
**Kind:** tech
**Lang:** python
**Roles:** model-training/alignment-and-rl @1

Each algorithm is a class you construct with a policy string, an environment and hyperparameters, then call `learn(total_timesteps)` on, with `save` and `load` for the model and callbacks for evaluation, checkpointing and early stopping. ### Stan
**Short:** Probabilistic programming language with industrial-strength HMC/NUTS sampling, driven from R, Python or the CLI.
**Kind:** tech
**Lang:** *
**Roles:** model-training/classical-ml-and-boosting @1, runtime-systems/collections-and-algorithms @3, applied-ml/interpretability-fairness-and-causal @3

### torchrun
**Short:** PyTorch's distributed launcher: spawns one process per GPU and sets RANK/WORLD_SIZE/MASTER_ADDR for NCCL rendezvous.

**Lang:** python
**Roles:** model-training/distributed-training @1, gpu/multi-gpu-and-collectives @2

### umap-learn
**Short:** UMAP dimensionality reduction for embedding visualization and clustering, with a GPU path via cuML.
**Kind:** tech
**Lang:** python
**Roles:** model-training/classical-ml-and-boosting @1, applied-ml/interpretability-fairness-and-causal @3, search-retrieval/ann-index-library @3

UMAP builds a weighted nearest-neighbour graph in the original space, using a locally adaptive distance so each point's neighbourhood is calibrated to its own density, then optimizes a low-dimensional layout whose graph matches it by attracting connected points and repelling sampled non-neighbours. `n_neighbors` sets how local that view is and `min_dist` how tightly points may pack; unlike t-SNE it exposes a `transform` for new points and can reduce to any target dimension, not only two.

### XGBoost
**Short:** Gradient-boosted decision tree library; the default tabular and learning-to-rank baseline, with CPU/GPU hist training.
**Kind:** tech
**Lang:** python, java, cpp
**Roles:** model-training/classical-ml-and-boosting @1, applied-ml/recommenders-and-graph-ml @2, gpu/gpu-math-libraries @3

Trees are grown over histogram-binned features with second-order gradients, missing values are handled by learning a default branch direction at each split rather than requiring imputation, and overfitting is controlled by shrinkage, row and column subsampling and explicit L1/L2 penalties. That combination is why it remains hard to beat on tabular data without heavy tuning, and why it is the baseline any deep-learning approach on tables has to justify itself against.

Tune depth, learning rate and subsampling together with early stopping on a genuine validation split, and remember trees cannot extrapolate outside the range they were trained on.

### XGBoost Dask

Watch data locality: partitions shuffling between workers each iteration erases the benefit.
